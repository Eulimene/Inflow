# 扩展包、运行时与能力代理

> 状态：设计草案，证据 `OPEN`
>
> 更新日期：2026-08-30

## 1. 扩展包

扩展包后缀为 `.inflow-extension`，本质是可重现 ZIP。根目录只允许：

- `manifest.json`：符合[扩展清单 v1 机器 Schema](../../quality/extensions/extension-manifest-v1.schema.json)；
- `manifest.sig`：对规范化 manifest 与内容根摘要的发布者签名；
- `components/`：清单逐项列出的 WebAssembly 或声明式资源；
- `licenses/`：许可证文本；每个普通文件必须在 `manifest.json.licenseFiles` 中声明路径、字节数与摘要。

未知根条目、绝对路径、`..`、NUL、重复规范路径、符号链接、硬链接、设备文件、加密 ZIP 和未在清单列出的条目一律拒绝。解包前后都检查条目数、单项大小、总展开大小、压缩比和嵌套深度。

### 1.1 身份与版本

- `extensionID` 使用发布者控制的 ASCII 小写反向域名，至少含一个点；每个 1–63 字节 label 只能含字母、数字和内部连字符，不能以连字符开始或结束，安装后不可变。`publisherID` 使用同一规则。
- 扩展/领域包的发布 `version` 严格使用 SemVer 2.0.0，包括合法的 prerelease 与 build metadata；数字 prerelease 标识不得有前导零，标识不能为空。同一 `(extensionID, version)` 只能对应一个内容根摘要；比较优先级时忽略 build metadata，优先级相同时再按完整版本 NFC UTF-8 字节序形成确定顺序。
- `publisherID` 必须与市场发布记录和签名证书绑定。
- `minimumHostVersion` 与领域包 `resolutionInput.hostVersion` 是 host compatibility release version，只允许无 prerelease/build 的 `major.minor.patch` 三段非负整数；扩展/包发布版本仍使用完整 SemVer 2.0.0。API 版本和组件摘要必须精确声明。
- v1 不支持插件到插件依赖；领域包解析后保存精确组件摘要，不在启动时重新求解。

领域包发布必须符合[领域包发布记录 v1 机器 Schema](../../quality/extensions/domain-pack-release-record-v1.schema.json)。市场在发布时一次性求解组件，将每个 `extensionID`、版本、组件 ID、API 版本、清单摘要和组件摘要固化到记录；安装与启动只验证这份精确解析结果，不重新选择“最新兼容版本”。该记录使用与市场发布记录相同的 JCS 和市场根签名规则，但签名字节的域分隔符固定为：

```text
"InflowDomainPackReleaseRecordV1\0" ||
SHA256(JCS(domain-pack-release-record.json))
```

`outputPolicy` 固定为 `core-declarative-content-tree-v1`；任何组件都不能借领域包获得 HTML、SVG、CSS、脚本、文件或网络输出能力。

`resolutionInput` 把 host/API 版本、市场 catalog snapshot 摘要、solver policy 版本以及每个请求组件的有限 `allowedVersions` 全部放进签名记录。数组按 `(extensionID, componentID)` 的 NFC UTF-8 字节序排列且组件键唯一，`allowedVersions` 按 SemVer 2.0.0 优先级再按完整版本 NFC UTF-8 字节序升序且不得重复；`resolutionInputSHA256 = SHA256(JCS(resolutionInput))`。Verifier 重新计算输入摘要，再要求 `resolvedComponents` 按同一组件键排序且唯一，其组件键集合与 `requestedComponents` **完全相等**；每项版本属于对应 allowed versions、API 版本匹配输入、摘要存在于被钉住的 catalog snapshot，且相同输入只能得到一份精确解析结果。缺项、多项、重复项或未请求项都整条拒绝。

`manifest.json` 必须是 UTF-8、无 BOM，并按 RFC 8785 JCS 规范化。所有整数长度都使用无符号 big-endian；文本都是 NFC UTF-8；下文的 `SHA256(x)` 均表示 32 字节原始摘要，不是十六进制文本。

`contentRootSHA256` 不包含 `manifest.json` 和 `manifest.sig`，避免自引用。对其余每个普通文件，以规范相对路径的 UTF-8 字节序排序，计算：

```text
leaf = SHA256(
  "InflowExtensionFileV1\0" ||
  u64be(pathByteCount) || pathBytes ||
  u64be(fileByteCount) || SHA256(fileBytes)
)

contentRoot = SHA256(
  "InflowExtensionContentRootV1\0" ||
  u32be(fileCount) || leaf[0] || ... || leaf[n-1]
)
```

ZIP 条目不能通过 Unicode、大小写或路径分隔归一后发生重复；所有允许的 `components/` 与 `licenses/` 文件都必须进入内容根。清单中的 `contentRootSHA256` 是 `contentRoot` 的小写十六进制。

`manifest.sig` 使用 Ed25519 对下列精确字节签名：

```text
"InflowExtensionManifestV1\0" ||
SHA256(JCS(manifest.json)) ||
contentRoot
```

验证密钥来自市场发布记录绑定的发布者身份，不信任包内自带证书。摘要字段全部使用小写非全零 SHA-256。

市场发布记录必须符合[市场发布记录 v1 机器 Schema](../../quality/extensions/market-release-record-v1.schema.json)。记录正文是 UTF-8、无 BOM 的 JSON，签名前按 RFC 8785 JCS 规范化；对应的分离签名使用市场根密钥对以下精确字节执行 Ed25519：

```text
"InflowMarketReleaseRecordV1\0" ||
SHA256(JCS(market-release-record.json))
```

`signatureAlgorithm` 固定为 `market-ed25519-jcs-v1`。客户端以受信市场根及其防回滚轮换链验证分离签名，并同时核对记录中的发布者证书摘要与包签名密钥；包内密钥、系统中任意其他受信证书或只有相同 `publisherID` 的声明都不能替代该绑定。未知字段因 Schema 闭世界而拒绝，`criticalFields` 中缺少 Schema 要求的关键字段同样拒绝。

`capabilitySetAlgorithm` 固定为 `manifest-capability-set-v1`。Verifier 从已验签 manifest 构造符合[清单能力集 v1 机器 Schema](../../quality/extensions/manifest-capability-set-v1.schema.json)的闭世界对象：`schemaVersion` 固定为 `1`；`requiredCapabilities` 与 `optionalCapabilities` 按 NFC UTF-8 字节序排列；`componentCapabilities` 按唯一 `componentID` 排列。每个组件项的字段精确为 `componentID`、`kind`、`imports`、`syntaxNamespaces`、`attributePolicies`；后者每项字段精确为 `namespace`、`sha256`，取对应 `attributeSchemas` 绑定的策略摘要并按 namespace 排列。缺省数组必须显式为空数组。随后计算 `capabilitySetSHA256 = SHA256(JCS(capabilitySet))`，并把完整 `capabilitySet` 与摘要一起写入发布记录。发布记录、安装提示和实际加载的能力集合必须使用同一结果；Verifier 还要求 manifest 的组件 ID 唯一，并要求 `resolvedComponents` 与 manifest 的组件 ID、kind、摘要和大小逐项完全一致。

清单将必需和可选能力分别放在 `requiredCapabilities` 与 `optionalCapabilities`；安装前展示必需项，未授权可选项不阻止其余能力。两组不得重叠。每个可执行组件还必须声明精确 `entryPoint` 和有闭枚举的 `imports`；语法 provider 另逐项声明 `inflow:<extensionID>:<name>` 形式的 `syntaxNamespaces`，并在 `attributeSchemas` 中为每个命名空间绑定包内属性策略的路径、摘要和字节数。该策略必须符合[语法属性策略 v1 机器 Schema](../../quality/extensions/syntax-attribute-policy-v1.schema.json)，也必须作为 `components` 条目进入内容根，路径/摘要/大小须完全一致。策略只允许闭世界 object、字符串/有限数字/布尔/字符串数组、enum、长度与数值上下界；不接受 `$ref`、远程引用、递归或正则表达式，最大 1 MiB；每个 namespace 恰有一份绑定。Verifier 必须交叉验证 `requiredProperties ⊆ properties`、所有上下界有序、allowed values 位于声明边界、`syntaxNamespaces` 与 `attributeSchemas.namespace` 集合相等且无重复、策略内 namespace 与绑定值相等。未声明 import、未知 import、命名空间越权、策略漂移和必需/可选重叠都在安装前拒绝。同一命名空间可由多个已验证 provider 声明，但安装不等于激活；Core 的版本化命名空间选择表在任一时刻只激活一个，首次冲突和后续切换均由用户明确选择。

### 1.2 验证与安装事务

1. 下载或用户选择的包先进入不可执行隔离区。
2. 一次性验证器只持有私有只读文件描述符；没有 Keychain、安装目录写权或用户文件权限。
3. 验证路径、ZIP 预算、清单闭世界、签名、发布记录、撤回状态和每个组件摘要。
4. 验证结果生成包含包摘要、内容根、策略版本和逐条目摘要的回执。
5. 安装管理器把已验证内容复制到应用私有内容寻址存储，移动前再次核对摘要。
6. 新版本完整落盘并通过启动前检查后，才原子切换活动指针；失败保留当前版本。
7. 已撤回版本不能通过回退恢复。

## 2. 普通插件运行时

### 2.1 进程边界

- 每个插件由独立宿主进程承载一个 WebAssembly 实例；宿主生命周期绑定插件任务，可按进程树终止。
- 宿主使用无网络、无用户文件、无 Keychain、无打印与无设备访问的最小沙箱。
- 不提供 WASI、环境变量、系统时钟精度、随机文件路径、动态库、进程创建或任意系统调用。
- Core 使用 audit token、指定要求、用户会话、连接 nonce、请求摘要和过期时间校验每个宿主连接；`extensionID` 只是声明字段，不是身份凭据。

### 2.2 IPC 信任矩阵

| Listener | 允许客户端 | 必需校验 | 明确拒绝 |
| --- | --- | --- | --- |
| Extension Launcher | Core App | designated requirement、audit token、UID/session、一次性 launch nonce、extension/content root | 仅凭 extensionID、其他登录会话、重放 nonce |
| Extension Host callback | 对应 Launcher client | 宿主 PID/audit token、launch nonce、connection ID、request hash、expiry | 同插件旧进程、其他插件宿主、过期 generation |
| Package Verifier | 一次性 Manager client | 指定要求、私有 FD、package hash、policy version、nonce | 路径字符串、Keychain 请求、安装目录写入请求 |
| Capability Authority | Core 管理的对应宿主 | audit token、capability token、用途/资源/request hash、expiry、replay cache | 插件声明身份、扩大资源、改变用途 |
| AI/Connector callback | 对应高信任 Launcher client | target designated requirement、PID/audit token、operation ID、nonce、request hash | 普通插件宿主、provider 返回的任意回调地址 |

所有 listener 默认拒绝未知消息和未知 critical 字段；连接建立通过不代表每个请求获准。每个请求重新绑定主体、资源和当前 generation。

### 2.3 资源预算

| 资源 | v1 上限 | 超限行为 |
| --- | --- | --- |
| 单任务输入 | 2 MiB UTF-8 或 10,000 个结构节点，先到者为准 | 拒绝并建议缩小范围 |
| 单任务输出 | 2 MiB UTF-8 或 10,000 个内容树节点 | 丢弃整次输出，不部分应用 |
| 线性内存 | 64 MiB | 终止实例 |
| CPU | 单次 500 ms，累计 2 s | 取消任务并记录超限 |
| 墙钟 | 5 s | 强制终止宿主进程树 |
| 并发 | 每插件 1、全局 4 | 公平排队，可取消旧 generation |

实际数值只有在目标机压力测试通过后才能从草案转为冻结合同。

所有 Extension、Render、Image、AI 和 Connector 宿主受同一个全局 Resource Governor 管理 RSS、CPU、并发、内存压力和按文档公平性；子系统局部上限不能相加突破全局预算。取消 generation 时同时取消其排队和运行任务。

### 2.4 输入与输出

- Core 只发送用户当前任务所需的不可变 UTF-8 选区、受限结构节点或无正文的文档属性。
- 请求绑定 `documentVersion`、`generation`、命令 ID 和授权范围；过期结果整次拒绝。
- 普通插件只返回纯文本编辑建议、诊断或 `ExtensionContentTree`。Core 验证范围、预算和语义后再呈现。
- 插件不能返回任意 HTML/SVG/CSS、文件 URL、脚本、系统命令或网络请求。
- 文本修改由 Core 生成差异，用户接受后作为一个撤销单元应用；插件不能直接接触编辑缓冲区。

## 3. 声明式界面

v1 界面节点仅允许分组、文本、图标引用、按钮、选择器、列表和进度状态。所有文本经过长度与 Unicode 检查，图标只能引用应用随包资产或市场验证资产。插件不能：

- 创建顶层窗口、系统对话框或覆盖编辑器；
- 自定义脚本、WebView、HTML、CSS、字体或远程图片；
- 模仿保存、授权、购买或系统安全提示；
- 在用户关闭视图后继续新任务。

## 4. SDK 与 API 兼容

扩展 SDK 只包含版本化 WIT/IDL、清单与内容树 schema、Core 语义 token、示例、离线验证器和测试运行器；不包含用户文件代理、网络客户端、市场私钥或应用内部 Swift 接口。

- Host API 使用 `major.minor`。未知 major 拒绝安装；相同 major 的新增 optional import 不能改变既有语义。
- 插件必须声明实际使用的 imports；未声明 import、未知 required import 和动态名称调用在加载前拒绝。
- SDK 测试运行器使用与发布应用相同版本的解析、预算和输出验证策略，并能生成可重现的测试回执。
- SDK 版本、编译器、源提交和依赖摘要进入构建 provenance；本地通过不替代市场签名和真实宿主沙箱证据。
- v1 不承诺二进制插件 ABI，也不允许链接应用私有 framework。

## 5. 能力代理

Core 为高信任、后续阶段能力签发一次性 capability token。token 绑定插件身份、用户会话、用途、资源范围、请求摘要、过期时间和 nonce，并由代理防重放。

普通市场插件 v1 不获得文件、网络、账号或费用代理。官方高信任 AI/连接器也不得直接读取用户目录或 Keychain；凭据由专用凭据所有者按单次操作提供，正文由 Core 通过认证、限额、可取消的流发送。

## 6. 更新、故障和卸载

- 边界不变更新可按用户偏好安装，但仍验证完整包和发布记录。
- 权限、发布者、数据去向、费用或兼容范围变化时，新版本保持未启用，直到重新确认。
- 崩溃、超时或输出违规只停止该插件；重复违规自动停用。
- 卸载先停止宿主、撤销 token、清除可再生缓存，再按数据矩阵处理设置和活动记录；绝不删除用户 Markdown。

## 7. 必需证据

- ZIP 路径和预算负面语料；
- 签名、摘要替换、安装中断与原子回退测试；
- 每扩展独立 PID、沙箱拒绝、网络拒绝和进程树强杀证据；
- 输入/输出、内存、CPU、墙钟、队列和 generation 取消测试；
- 任意 HTML/SVG/CSS/脚本输出拒绝语料；
- 撤回版本不可安装、启用或回退的端到端测试。
