# 明文恢复与多进程接管

本阶段优先实现编辑、手动保存、异常恢复。运行中的应用使用明文 JSON 草稿，不需要密钥或钥匙串，也不使用跨进程文件锁、租约或等待队列。

## 用户行为

- 最近激活的 Inflow 进程获得编辑和保存优先级；切回另一个进程即可接管，不等待原进程释放锁。
- 后台进程通过现有文件监测发现磁盘内容变化后重新加载。接管时也会重新检查磁盘内容。
- 重新加载前，若本地有未保存内容，先将其保留为独立的恢复草稿。写草稿或读取磁盘失败时保留编辑器原文，并保留现有冲突提示供重试。
- 草稿保护不会自动保存用户的 Markdown 文件；仍使用 ⌘S 保存。
- 后台进程暂停共享恢复目录的写入，不因失去优先级显示“恢复保护暂时不可用”；重新激活后恢复工作。

## 存储与范围

相对于应用的 Application Support 目录：

| 路径 | 用途 |
| --- | --- |
| `Inflow/DevelopmentDrafts/*.json` | 开发版明文恢复草稿 |
| `Inflow/RecoveryDrafts/*.json` | 正式版明文恢复草稿 |
| `Inflow/ProcessOwners/*.owner` | 每个进程独立的激活时间、PID 和活动草稿 ID |

草稿目录权限为 0700，文件为 0600。写入采用临时文件加原子替换。关闭标记只用于忽略尚未完成的旧写入，不用于加锁或等待。损坏的 JSON 保留在原处，不阻塞其他可用草稿。

现有 SessionDrafts 继续承担关闭检查点及重新加载前的独立备份。旧 `Recovery`、`DevelopmentRecovery` 加密目录保留，本次不自动迁移或删除；旧加密实现只保留为兼容组件，运行入口使用明文存储。

优先级检查发生在写入准备和实际草稿写入前。进程状态约每 0.5 秒检查一次，已有文件监测约每秒一次。这是应用实例之间的协作机制，不承诺阻止任意外部程序写入，也不提供已经进入系统文件写入阶段的强制事务撤销。

## 启动恢复

启动首个编辑页面后，后台扫描草稿文件名和修改时间，只建立内部候选列表，不立即创建标签。后台验证后，只有确实需要恢复的草稿才以真实名称进入标签栏；空草稿、与磁盘文件一致的副本、已由其他记录接管的源记录不会先出现再消失。显示过滤不删除草稿数据。

后台最多并发验证 4 份候选，读取、解码和校验不在主线程执行；一份慢草稿不会阻塞同批其他草稿显示。已显示的标签复用准备结果，仅在被选中时创建完整编辑器，其他标签保持轻量状态。同一草稿的读取和接管分别去重。重新激活进程不会重复扫描整个临时工作区。

读取失败的候选仍显示轻量标签和重试入口，保留原始数据，其他编辑页面仍可使用。明确关闭恢复标签会取消后续恢复并标记丢弃，防止下次启动再次出现。占位文档禁止保存，防止用空白内容覆盖草稿。临时检查点只有在恢复目录持久接管后才移除，新的编辑器写入自己的恢复记录前仍保留源记录；恢复时会再次检查源记录，拒绝覆盖后台读取之后产生的新版本或其他恢复请求。明确清空恢复内容时，取消待加载的标签，并使当前扫描批次失效，防止尚未完成的发现或读取任务重新创建已清除内容。
