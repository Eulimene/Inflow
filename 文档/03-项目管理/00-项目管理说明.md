## 1. 目的

本目录统一 Inflow 的文档管理、产品决策和变更追踪方式，解决以下问题：

- 某个产品语义、默认值、范围或验收条件由哪份文档决定。
- 文档何时只是草案，何时已经可作为项目基线。
- 新需求、范围变更、默认值调整和例外如何被评审、记录和通知。
- 市场研究、竞品证据、规格附录和决策记录如何参与决策，又不篡改产品范围。

## 3. 权威层次

### 3.1 自上而下的权威链

1. **产品愿景与原则**：定义为谁解决什么问题、长期价值和不可牺牲的产品原则。
2. **产品需求与专项产品设计**：定义用户行为、范围、版本归属、交互语义和验收结果。
3. **产品规格与规格附录**：将已批准的产品语义编码为精确选项、状态、默认值、范围和例外。
4. **产品决策与变更记录**：保留重要取舍、理由、替代方案、文档变化和后续复审条件，不替代产品正文。

当前 `文档/` 只保存人可阅读的产品设计、产品规格、市场与迁移研究、规格附录和项目管理 Markdown。任何其他类型的内容都不在本文档库的权威链中。

本节权威链与[文档中心](../00-文档中心.md)的权威关系由全库正式文档自动继承。专项文档通过文档头中的权威范围与关联文档，或独立权威章节标明自身责任即可，不需要逐篇复制相同的冲突处理语句。

### 3.2 市场研究的边界

市场研究、竞品观察、用户访谈和迁移证据是**决策输入**，不是产品范围权威。它们可以：

- 提出用户问题、迁移风险和行业预期。
- 支持或挑战一个已提出的产品假设。
- 为验收样本和成功指标提供来源。

它们不能：

- 因为“其他产品已有”而自动创建需求或扩大版本范围。
- 将竞品菜单、界面、术语、视觉或交互顺序转成 Inflow 设计规格。
- 覆盖已批准的用户默认值、安全边界或产品反目标。

产品负责人可依据已明确的用户问题、产品原则、风险边界和可验收结果批准产品文档。固定数量的访谈、迁移样本、测试轮次或价格研究不是文档批准、0.1 公共预览版或正式 1.0 的前置门槛。产品发布后，通过用户主动反馈、用户选择参与的研究和主动诊断包持续验证决策；不使用遥测或后台使用数据发送代替。这一规则不降低安全、隐私、产品 UAT 和分发候选证据的发布门槛。

### 3.3 附录的权威边界

当产品规格将具体默认值、取值范围、选项集、状态转移或例外清单委托给某份附录时，该附录是**这些规格字段的唯一默认值权威**。

主产品文档仍然决定“为什么存在、用户能感知什么、属于哪个范围”。附录不得创建新功能、更改版本归属或扩大权限。主文与被委托附录不一致时，视为发布阻断，必须通过正式变更同步修正，不允许任一方静默覆盖另一方。

### 3.4 全库冲突处理

任何产品语义、范围、默认值、状态、例外或验收冲突都阻断候选基线与发布。负责人先按[文档中心](../00-文档中心.md)与本节的权威链确认责任文档，再依据[文档管理规范](./01-文档管理规范.md)补齐必要决策与变更记录，正式修订全部受影响文档；不得按更新时间、文档层级或描述详略静默选择一方。该规则由全库自动继承，不因专项文档未重复声明而失效。

## 4. 文档状态

正式文档只使用以下四种状态：

| 状态 | 含义 | 可否作为基线 |
| --- | --- | --- |
| 草稿 | 负责人正在形成方案，内容可大幅调整 | 否 |
| 待评审 | 范围完整，正在等待指定角色审核 | 否；只作为评审候选 |
| 已批准 | 已完成必要评审，可作为项目基线 | 是 |
| 已废止 | 已被新文档或新决策取代，仅供追溯 | 否 |

不使用“定稿”“冻结”“完成”“已验证”等词作为文档状态，避免把内容批准与产品实际交付混为一谈。

## 5. 基本工作流

```mermaid
flowchart LR
    A["问题与证据"] --> B["草稿"]
    B --> C["待评审"]
    C -->|"通过"| D["已批准"]
    C -->|"需要修改"| B
    D -->|"被取代"| F["已废止"]
```

1. 问题发起人提交用户问题、证据、影响和建议边界。
2. 文档负责人形成草稿，核对权威来源、受影响文档和用户可见结果。
3. 进入待评审前，必须补齐文档头、本地链接、验收条件、决策与变更记录。
4. 评审人按内容类型检查用户价值、交互、数据安全、可访问性、范围和可验收性。
5. 已批准文档形成产品文档基线；文档批准不等于功能已交付、用户验收已通过或版本已发布。

## 6. 角色与责任

| 角色 | 责任 |
| --- | --- |
| 提议人 | 提交问题、证据、建议与受影响用户 |
| 文档负责人 | 保证内容完整、权威边界清楚、链接和版本正确 |
| 产品负责人 | 批准用户价值、范围、默认行为和验收结果 |
| 专项评审人 | 对安全、隐私、可访问性、商业或合规影响给出明确结论 |
| 项目管理人 | 检查编号、状态、变更记录、评审完整性和取代关系 |

一个人可承担多个角色，但涉及扩大范围、敏感数据、外部费用或不可逆用户影响的变更，不能只由文档作者自审批准。

## 7. 发布与复审规则

- 候选发布只能使用“已批准”的范围、默认值和验收标准。
- 任何待评审文档若被候选发布依赖，必须先完成批准或明确移出范围。
- 已批准文档在重大用户反馈、验收结果变化、安全事件、法规变化或上位原则更新后重新评审。
- 定期复审至少核对负责人、外部链接、默认值、版本兼容、已知例外和被取代关系。
