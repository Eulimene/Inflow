# Inflow 阅读材料中心

本目录只保存供人阅读的 Markdown 文档，并按“产品定义、技术实现、治理追踪”归类。JSON、JSON Schema、机器策略和校验实例统一放在相邻的 [`机器校验`](../机器校验/) 树中，避免人读说明与机器合同混放。

## 三个主入口

| 领域 | 回答的问题 | 入口 |
| --- | --- | --- |
| 产品 | 做什么、为谁做、版本范围、产品规格与特性是什么 | [产品文档](./产品/说明.md) |
| 工程 | 如何实现、如何隔离、如何验证和发布 | [技术文档](./技术/说明.md) |
| 治理 | 评审意见是否闭环、需求如何映射到工程证据 | [治理文档](./治理/说明.md) |

## 权威关系

1. [PRD](./产品/产品需求文档.md) 决定产品语义、版本范围和 DoD。
2. 产品规格、对标与能力清单补充用户可见能力，不覆盖 PRD。
3. [总体技术设计](./技术/技术设计.md)、Core 合同和扩展技术合同决定实现与机器约束，不改写产品范围。
4. [需求追踪表](../机器校验/治理/需求追踪.json)只映射 requirement、owner、阶段和证据；[复审台账](./治理/最终评审闭环.md)只记录处置状态。

## 阅读约定

- 产品讨论从 `文档/阅读材料/产品/说明.md` 开始；不要先加载实现细节。
- Core 实现从总体技术设计开始，再进入 `文档/阅读材料/技术/核心/` 的专项说明；机器约束在 `文档/机器校验/技术/核心/`。
- 扩展问题先区分产品开放边界与技术实现：前者读产品规范，后者读扩展工程入口。
- 人工阅读默认从本树进入；脚本与 CI 应直接读取 `文档/机器校验/`，不要解析 Markdown 投影来替代机器源。
- 阶段是否完成必须同时满足产品 DoD 和候选 Release 的真实机器证据；合同定稿本身不等于 T0/P0 完成。
