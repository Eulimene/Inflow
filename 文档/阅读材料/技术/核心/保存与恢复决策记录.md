# SaveRecovery ADR（P0 冻结契约）

- ADR 状态：Accepted（架构决策已冻结）
- 验证状态：OPEN（本文件末尾的 T0 故障矩阵尚须由 Release fixture 通过）
- 适用：P0 保存、自动保存、关闭、Save As、外部修改与 Recovery
- 机器事件契约：[`恢复日志事件模式.json`](../../../机器校验/技术/核心/恢复日志事件模式.json)

“Accepted”只表示实现不得再自行选择另一套保存生命周期；不表示 T0 已完成，也不解除 T1 阻断。

## 1. 唯一外层保存事务

选择原生 `NSDocument.save(to:ofType:for:completionHandler:)` 作为唯一外层保存入口。`SaveCoordinator` 不直接调用 `writeSafely`、`replaceItemAt` 或自建 safe-write；`NSDocument.writeSafely(to:ofType:for:)` 仅是原生 save 内部唯一允许到达的物理 writing primitive。

菜单保存、关闭屏障、应用发来的 save operation、首次保存、Save As 和应用自己的文件自动保存全部先形成 `SaveIntent` 并进入每文档唯一的 `SaveCoordinator`。Coordinator 完成 Recovery 准备和目标 guard 后，在 MainActor 安装一次性 `NativeSaveReentryToken`，再调用原生 save。所有 `NSDocument` override 遇到没有有效 token 的入口都只回投 Coordinator；只有绑定当前事务的 token 可以进入 `super.save(...)`。token 包含 `saveNonce / documentID / operation / canonicalTarget / contextID`，线程安全、不可复制、最多消费一次，完成或取消即撤销。

AppKit 独占以下生命周期：

- change-count/save change token 的获取与结算；Coordinator 不手工清零 change-count。
- Safe Save 的 staging、文件协调与原子替换。
- `.saveAsOperation` 成功后的 `fileURL` 切换。
- 原生保存完成回调的语义。

实现若发现必须绕过上述任一项，须先批准新的 `DocumentWriteTransaction` ADR；不得把两条路径同时留在产品代码中。

## 2. SaveEnvelope 与 CommitContext

执行某个意图时，在 MainActor 一次捕获不可变：

```text
SaveEnvelope {
  saveNonce, documentID, documentVersion, exactData, contentHash,
  lineEnding, BOM, operation, canonicalTarget, targetExpectation,
  relativeReferenceImpactPlanID?
}
```

`CommitContext` 是围绕同一 envelope 的加锁状态机，而不是全局可变的“当前保存数据”：

```text
issued → nativeEntered → writing → nativeCompleted
       → diskVerified → baseAdopted → journalCommitted → settled
                   ↘ externalConflict
                                   ↘ diskCommittedJournalPending
原生 completion 前失败 → aborted
```

- context 必须同时匹配 `contextID + saveNonce + documentID + operation + target`；`data(ofType:)` 和 `writeSafely` 不得按“最近一次 context”猜测。
- 只有持有 re-entry token 的原生 save 可以把 `issued` 推进到 `nativeEntered`；只有该次原生调用可以一次性取得 writing lease。
- `data(ofType:)` 在 lease 有效期间只返回 envelope 的 `exactData`。缺失、过期、重复或目标不匹配均失败，不得重读变化中的 TextBuffer。
- context 可被 AppKit 的内部调用读取多次，但物理 writing lease、原生 completion 结算和 token 消费各自严格一次；并发或晚到完成回调只得到 `staleContext`。任何 Recovery 后处理都不得第二次进入原生 save。
- context 完成后立即清除明文字节引用；Recovery blob 按独立生命周期保留。

固定顺序为：capture envelope → 尝试 durable Recovery slot → 建立 `pendingSaveNonce` → target guard → 安装 re-entry token → **恰好一次**原生 save/writing primitive → 原生 completion → 协调读取并验证实际 identity/revision/hash → 精确结算 self-write 事件 → `adoptCommittedBase` → 尝试 durable `saveCommitted` → 结算 Recovery facet。journal 追加属于原生生命周期之后的 Recovery 后处理，不能回滚、重放或伪造 AppKit completion。

AppKit 在原生 completion 中结算 change-count 和 Save As `fileURL`；Coordinator 不重复操作。磁盘 postflight 精确匹配后记录 `savedVersion` 并采用 committed base；只有 `savedVersion == currentBufferVersion` 且目标仍是当前 `fileURL` 时，应用 dirty barrier 才为 clean。较新编辑、较新意图或旧 completion 不得被清除。postflight 不匹配表示 completion 后发生外部替换，立即进入 conflict，不采用错误 base；它不靠倒改 AppKit completion 来掩盖竞态。

## 3. 磁盘已提交但 journal 未提交

原生 completion 已成功、目标 identity/revision/hash 已验证且 committed base 已采用，但 `saveCommitted` 追加或 `fsync` 失败时，Recovery facet 固定为：

```text
diskCommittedJournalPending {
  envelope, actualFileRevision, actualHash, operation, firstFailure
}
```

此时必须同时满足：

- 对用户明确显示“文件已保存，恢复记录待确认”；文件保存结果仍是成功，不把 Recovery `fsync` 失败冒充为用户文件失败。
- AppKit change-count、Save As `fileURL`、`savedVersion` 和 committed base 保持已完成状态；journal pending 本身不制造 dirty，也不阻止正常关闭。
- 保留 prepared blob 与 pending 记录，只重试 journal 追加/`fsync`。禁止第二次原生 save、no-op writer、`nativeLifecycleReplay`、手工 change-count 或 `fileURL` 回滚。
- self-write 已在磁盘 postflight 后独立精确结算，不等待 journal，也不因 journal 失败重放或吞掉 FilePresenter 事件。
- 后续文件 save 仍可执行：先尝试修复旧 pending；仍失败则把 Recovery 标为 degraded，并在没有新 Recovery slot 的情况下执行下一次原生 save。Recovery 故障不能反向锁死用户文件。
- 重试时目标仍精确匹配 `actualFileRevision + actualHash` 才追加 committed；若已外部变化则保留 prepared blob/不确定标记并进入外部冲突，禁止覆盖或 replay。

进程在该状态崩溃时，磁盘上只存在 durable `savePrepared`。启动回放按目标的实际 revision/hash 对账：精确匹配则追加带 `reconciledAfterCrash=true` 的 `saveCommitted`；不匹配则保留 blob 并标记“保存结果不确定”。这一定义只修复 Recovery 账本，不重新执行已经完成的用户文件保存。

## 4. Recovery 不得反向锁死用户文件

Recovery 是辅助保护层。Keychain 锁定/密钥缺失、Recovery 卷空间不足、blob/index/journal 损坏或 `fsync` 失败时，Coordinator 进入可见的：

```text
recoveryProtectionDegraded(reason, since, affectedDocumentVersion)
```

随后仍允许原生 save 写用户选择的 `.md` 文件；Recovery 失败不得改变目标 guard，也不得被包装成用户文件保存失败。此次保存没有 durable prepared slot，UI 和诊断必须明确说明崩溃保护降级；降级解除前不宣称“可自动恢复”。未命名文档没有用户文件目标，因此只保留内存内容、持续提示并禁止伪装成文件自动保存。

密钥错误分支固定如下：

- `interactionNotAllowed/Keychain locked`：保留原 store，不删除 key、不生成替代 key；解锁后重试。
- 已确认 `itemNotFound` 或认证永久失败：把旧 journal/blob/index 原子移入不可自动读取的 `Recovery/Quarantine/<storeGeneration>/`，生成新的 store generation 与 Recovery KEK，再建立新 head；旧密文只提供删除或显式人工恢复入口。
- 新 key 或新 head 未 durable 前保持 degraded；不得覆盖旧密文后继续。

配额只计算历史 checkpoint。每个 active document 的“唯一可恢复 head”和“当前 pending-save slot”均不计入历史配额，回收器不得删除；历史仍受单文档 256 MiB/2,000 条、全应用 2 GiB 限制。任意大文档或物理 `ENOSPC` 不能由逻辑配额保证成功：分配失败就降级 Recovery，并继续尝试用户目标卷的原生 save。文案不得承诺无限容量。

## 5. Journal 布局、记录与轮换

唯一布局为：

```text
Application Support/Inflow/Recovery/
├── index.sqlite
├── sessions/<documentID>/<epoch>.journal
├── anchors/<documentID>/<epoch>.anchor
├── blobs/<documentID>/<blobID>.bin
└── Quarantine/<storeGeneration>/...
```

一个 journal 文件只属于一个 `(documentID, epoch)`。epoch 内轮换使用追加的 `segmentStart` 与完整 `checkpoint` 记录；不得创建语义不明的“每 document 公共日志”，也不得用轮换隐式生成新 epoch。active epoch 的文件保持 append-only，不原地删除 prefix、改写或压缩；`segmentStart/checkpoint` 只界定校验和回放窗口。物理空间只在 epoch 已 durable `clean`、`consume` 或 `retire+discard` 且无引用后回收整份文件；若 active journal 达到实现冻结的字节/记录上限，必须通过本 ADR 第 6 节同一 pending→activate→consume handoff 建立新 epoch，不能偷偷改写当前 journal。

wire 只有 v1，整数均为无符号 big-endian，UUID 为 RFC 4122 的 16 个 network-order bytes，可变字段使用显式长度前缀，不存在平台结构体 padding。header 字段顺序固定为：

```text
JournalHeaderV1 {
  magic="IFRJ", wireSchemaVersion=1, minimumReaderVersion=1,
  headerLength, storeGeneration, keyIDLength, keyID,
  opaqueDocumentIDLength, opaqueDocumentID, epoch,
  createdAtUnixMilliseconds, journalKeySalt[32], headerCRC32C
}
```

`headerLength` 精确等于从 magic 到 `headerCRC32C` 末尾的字节数。`headerCRC32C` 覆盖它之前的全部 header bytes；`canonicalHeaderDigest = SHA-256(header bytes excluding headerCRC32C)`。`keyID` 精确指向当前 Recovery namespace DEK wrapper 版本，`storeGeneration` 必须与该 wrapper 及 `start.storeGeneration` 一致。任一长度、CRC、编码、keyID 或 generation 不匹配都在解密前拒绝。

Recovery domain KEK 只包装 `(opaqueDocumentID, storeGeneration)` namespace 的随机 256-bit DEK。journal record key 从该 namespace DEK 以 HKDF-SHA-256 派生，`salt=journalKeySalt`，`info` 为 Data Protection Policy 固定的 length-prefixed `com.inflow.dataprotection/v1/journal-record` label，再连接 length-prefixed role `record` 与 opaqueDocumentID/storeGeneration/epoch/keyID。不得直接把 domain KEK 当 record key。

```text
JournalRecordFrameV1 {
  frameLength, sequence, segmentID, previousRecordHash[32],
  plaintextLength, ciphertextLength, nonce[12], ciphertext,
  gcmTag[16], recordCRC32C
}
AAD = lengthPrefix("IFRJ-record-v1") || canonicalHeaderDigest ||
      frameLength || sequence || segmentID || previousRecordHash ||
      plaintextLength || ciphertextLength
```

payload 是 canonical CBOR，加密前必须通过 [`恢复日志事件模式.json`](../../../机器校验/技术/核心/恢复日志事件模式.json)。`nonce` 每条由 CSPRNG 随机生成 96 bit，同一派生 key 内发现重复即拒绝 append；不得从 sequence 截断或重用 nonce。frame 中的 sequence/segmentID 必须与解密 event 同名字段数值一致，wire `previousRecordHash[32]` 必须与 event 中小写 64-hex `previousRecordHash` 解码后的字节一致；`plaintextLength` 等于 canonical CBOR 字节数，event 的 `payloadLength` 等于仅对该 kind 专属字段做 canonical CBOR map 编码的字节数。`frameLength` 精确包含整条 frame，`ciphertextLength == plaintextLength`。`recordCRC32C` 覆盖它之前的全部 frame bytes，后一条 `previousRecordHash` 是前一条包含 CRC 的完整 frame SHA-256；sequence 1 的值固定为 32 个 zero byte。

追加顺序固定为“写入完整 frame → `fsync(journal)` → 原子替换并目录 fsync tail anchor”。anchor wire 固定为 `magic="IFTA", version=1, frameLength, nonce[12], ciphertextLength, ciphertext, gcmTag[16], anchorCRC32C`；解密明文是不允许未知字段的 canonical CBOR map `JournalTailAnchorV1 {canonicalHeaderDigest, fileLength, lastSequence, lastRecordHash}`。anchor key 使用同一 `journalKeySalt` 和 `journal-record` label，但 role 固定为 `tail-anchor`；nonce 同样为 CSPRNG 随机 96 bit。AAD 固定为 `lengthPrefix("IFRJ-tail-anchor-v1") || canonicalHeaderDigest || frameLength || ciphertextLength`，CRC32C 覆盖 tag 在内的前述全部 anchor bytes。崩溃后 journal 可比 anchor 更长，但额外后缀必须从 anchor hash 连续验证才可接纳并推进 anchor；journal 比 anchor 短、链分叉、完整 frame 被删除或 anchor 损坏/缺失都不得自动恢复。只有末尾不完整、tag/CRC 未成立且位于已认证 anchor 之后的 torn frame 可整帧截去；不返回部分明文。这些 length/AAD/tag/hash-chain/anchor 规则共同构成抗截断契约，SQLite 仍只是可重建索引。

解密后 event 的公共字段严格为 `schemaVersion, kind, opaqueDocumentID, epoch, segmentID, sequence, timestamp, previousRecordHash, payloadLength`；人类文档中的花括号只可省略这些公共字段。下列 kind 专属字段不得别名或增补：

- `segmentStart { coveredCheckpointRecordHash }`；新 segment 的唯一编号是公共 `segmentID`，不得定义第二编号字段。
- `start { initialState, storeGeneration, baseSavedDocumentVersion, baseFileRevision, replacesEpoch?, handoffID? }`；后两项在 pending 时必需且仅 pending 可出现，active 时必须缺省。
- `savePrepared { saveNonce, blobID, documentVersion, snapshotGeneration, targetIdentity, targetExpectation, contentHash }`。
- `saveCommitted { saveNonce, blobID, documentVersion, contentHash, actualRevision, reconciledAfterCrash }`。
- `consume { consumedByEpoch, handoffID, activateRecordHash, throughGeneration }`。

`savePrepared` 的 `blobID` 必须指向可持久恢复 exact envelope 的 blob；`saveCommitted` 必须与 prepared 的 `saveNonce/blobID/documentVersion/contentHash` 全部相同并携带实际 target revision。

## 6. epoch handoff：pending → active → consumed

普通新会话以 `start { initialState: active, storeGeneration, baseSavedDocumentVersion, baseFileRevision }` 开始。从旧 epoch 恢复时使用不可伪造的 `handoffID` 和以下唯一顺序：

1. 在旧 journal 同步 `handoffPrepared { handoffID, newEpoch, throughGeneration }`；它只预留 handoff，不改变旧 epoch 的资格。
2. 创建新 `<newEpoch>.journal`，同步 `start { initialState: pending, storeGeneration, baseSavedDocumentVersion, baseFileRevision, replacesEpoch, handoffID }`。
3. 写入新 epoch 首个 durable blob/index/head；新 epoch 此时仍不得单独进入恢复中心。
4. 把 exactData 应用到 TextBuffer；失败则旧 epoch 保持 active，新 pending 留待清扫。
5. 在新 journal 同步 `activate { replacesEpoch, handoffID, headGeneration, headHash }`。这是唯一恢复资格切换点；新 epoch 从 pending 变 active，并立即压制旧 epoch。
6. 在旧 journal 同步 `consume { consumedByEpoch, handoffID, activateRecordHash, throughGeneration }`，再向 UI 确认完成。

回放规则保证唯一候选：

- 没有有效 `activate` 时，旧 active 胜出，新 pending 不可自动恢复。
- 有效 `activate` 必须认证 `replacesEpoch + handoffID + 已 durable 的 headGeneration/headHash`；它足以使新 epoch 成为唯一 effective-active，即使进程在 old consume 前崩溃。
- old `consume` 只完成被替代 epoch 的显式终态，并用 `activateRecordHash` 交叉验证；缺失 consume 不得让旧 epoch 重新获得资格。
- 同一 `replacesEpoch` 出现多个有效 activate、handoffID/head 不匹配或出现分叉时进入人工隔离，不能按时间戳猜测；正常 actor 必须保证唯一 handoff。

`retire` 先关闭 epoch 的任务入口；`discard` 再记录水位。`retire` 单独 durable 即禁止自动恢复，UI 只有在两者均同步后才确认“已放弃”。`clean`、`consume` 或 `retire` 后的晚到任务必须在写临时 blob、rename 和索引事务三个边界再次校验 epoch 状态并自弃。

## 7. FilePresenter 与 self-write 判定

在 target guard **之前**建立 `pendingSaveNonce { nonce, target, expectedRevision, startSequence }`。保存期间到达的 FilePresenter 事件只暂存，不提前归因为自身写入。

磁盘替换后，Coordinator 读取实际 revision/hash：

- 只有绑定同一 nonce、target、实际 revision 和 envelope hash 的事件可由最终 `selfWriteToken` 精确消费。
- guard 前事件、实际验证之后的新 revision、乱序但 identity/hash 不匹配的事件全部作为外部修改继续处理。
- 原生 completion 后磁盘 postflight 一旦精确匹配就立即产生并结算最终 token；`diskCommittedJournalPending` 是独立 Recovery facet，不延迟或改变该判定。
- 完成、失败、取消或超时必须撤销 pending nonce，并重新扫描目标 revision；不能通过暂停 FilePresenter 丢事件。

## 8. Save As 与文档所有权

全局 `DocumentRegistry` actor 同时按 canonical URL 和文件 resource identity 去重。Save As 在生成 envelope 前取得目标 reservation；目标已由另一 `DocumentSession` 拥有时中止并聚焦现有会话。不存在的目标按“父目录 identity + 规范化文件名”预留，写后绑定实际 resource identity；reservation 持续到原生 completion 与元数据结算完成。

跨目录 Save As 必须先生成：

```text
RelativeReferenceImpactPlan {
  planID, sourceDocumentVersion, sourceContentHash,
  sourceDirectoryIdentity, targetDirectoryIdentity,
  impactedReferenceNodeIDs, rawReferenceHashes,
  dependencyExpectations[{nodeID, oldResolution, newResolution,
                          observedParentIdentity, observedResourceIdentity?, observedRevision?}],
  dependencySetHash, decision
}
```

计划绑定 source version、两个目录 identity 和每条相对引用在源/目标位置的存在性、授权结果、resource identity 与 revision expectation。进入原生 save guard 前必须从已授权目录 FD 逐项重新解析并比较 `dependencySetHash`；正文、目录、保存目标或任一依赖文件发生创建/删除/移动/替换/修改/撤权，都作废并重新分析、展示和确认。没有已确认且仍匹配的 plan，跨目录 Save As 不得进入 Recovery prepare。

alias 记录为 `{canonicalURL, resourceIdentity?, state: pending|active|retired, validFromEpoch, retiredAt?}`，每个 documentID 恰有一个 active alias。旧路径在 Save As 成功后转 retired，未来出现的新文件不得复用该 documentID。原生 save 是 `fileURL` 的唯一修改者；持久元数据在原生 Save As 前写 pending intent，成功并复核实际 target 后原子执行“新 alias active、旧 alias retired、bookmark/revision 更新”。若磁盘和原生 `fileURL` 已提交而元数据事务失败，统一进入 `metadataReconciliationPending`，保留两侧 scope 与 registry reservation，只重试元数据，不回滚或重写用户文件。

## 9. 自动保存、base 与 Undo

文件自动保存的 eligibility 固定为：`named && writable && current target exists && no conflict && state != metadataReconciliationPending`；同一 Coordinator 仍串行执行原生事务。`metadataReconciliationPending` 期间也禁止再次 Save As，直到 registry/bookmark/revision 按已提交的 `fileURL` 对账完成。Recovery degraded 或 `diskCommittedJournalPending` 不取消其他合格文档的资格，必要时保存以无 Recovery slot 的降级方式继续。未命名、已删除、只读或冲突中的文档不发起 `.saveOperation`；未命名文档只写 Recovery head。关闭 AppKit autosave/draft/Versions 的既有决定不变。

open、验证成功的 save、自动 reload 与用户确认的 revert 全部调用唯一：

```text
adoptCommittedBase(reason, exactData, contentHash, fileRevision, documentVersion)
```

reload/revert 必须先再次校验开始时捕获的 buffer version 与磁盘 revision，再原子替换 TextBuffer、采用 base、恢复语义位置并清空该文档 Undo/Redo；替换前后的 Undo action 不得跨越新的磁盘事实。save 不替换正文，因此采用 base 但保留正常编辑 Undo；open 从空 Undo 开始。

## 10. T0 必过故障矩阵

- 所有 `NSSaveOperationType`、菜单/关闭/自动保存/Save As 都进入一次原生 outer save，无法绕过 envelope，也没有第二个物理 writer。
- 捕获、Recovery blob/head、prepared、target guard、替换、原生 completion、实际 hash 校验、base adoption、committed 与 metadata finalize 每个边界强杀并正确回放。
- 专门注入“原生 completion/磁盘后验成功、`saveCommitted` fsync 失败”，验证 `diskCommittedJournalPending` 不改变文件成功、change-count、Save As `fileURL` 或 self-write 判定，且绝不触发第二次 native save。
- Keychain locked、key missing、Recovery `ENOSPC`、损坏 journal/index/store 均显示 degraded，但 named 文件仍可保存；未命名文档绝不产生普通文件。
- handoff 在 pending head、应用 TextBuffer、new activate、old consume 每个边界强杀，恢复中心始终只选一个 epoch。
- guard 前/中/后 FilePresenter 乱序、同内容外部替换和 resource identity 变化均不误吞事件。
- Save As 目标已被其他 session 打开、absent→created、revision 改变、跨目录 plan 失效、bookmark/alias 事务失败、scope 释放失败均保持唯一所有权。
- reload/revert 后 base、dirty、selection 和 Undo/Redo 与新磁盘事实一致。

任一 fixture 出现静默覆盖、正文不可恢复、重复恢复、错误清除 dirty、错误切换 `fileURL` 或 Recovery 故障阻止 named 文件保存，本 ADR 的验证状态保持 OPEN，T1 不得开始。
