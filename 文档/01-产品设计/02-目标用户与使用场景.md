## 1. 文档目的

本文定义 Inflow 的目标用户、核心任务、使用情境和成功结果。它回答“谁会在什么情况下选择 Inflow，以及产品必须帮助他完成什么”，作为功能取舍和版本优先级的用户依据。

本文不以职业标签代替需求判断。同一个人可能在不同任务中属于不同用户类型；优先级由内容寿命、结构复杂度、交付频率和对文件控制权的要求共同决定。

## 2. 核心用户特征

Inflow 的核心用户通常同时具备以下三项或更多特征：

- 把 Markdown 用于需要数月或数年维护的真实内容；
- 希望文件直接保存在自己选择的位置，并能被其他工具继续使用；
- 经常在精确源码、即时反馈和完整阅读之间切换；
- 文档包含多层标题、链接、图片、表格、代码、公式或其他结构；
- 需要把文档稳定地分享、归档或交给下一环节；
- 对静默覆盖、版本混淆、资源缺失或隐私外发较敏感；
- 愿意使用高级能力，但不愿让这些能力成为写作和文件所有权的前提。

## 3. 目标用户分层

### 3.0 当前验证用户

个人首版只服务一名验证用户：产品负责人本人。当前阶段的目的，是用自己的一个真实 Markdown 项目和真实日常任务确认目录导航、项目内引用、即时渲染写作与文件安全是否值得继续投入；它不代表已经验证了更广泛用户群、公开安装流程、设备兼容或支持体系。下列长期目标用户仍用于约束产品方向，在进入公共预览前再通过独立决策确认实际招募范围。

### 3.1 核心用户

#### A. 长期资产写作者

典型角色包括技术作者、独立创作者、开发者文档维护者和个人知识资产管理者。

- **主要目标**：持续形成、维护和交付一组属于自己的 Markdown 内容。
- **当前阻力**：编辑工具容易关注单次输入，却无法清楚处理长期保存、结构演进和反复交付。
- **选择 Inflow 的理由**：本地文件始终可带走，日常写作与长期维护使用同一条工作流。

#### B. 结构化专业写作者

典型角色包括产品经理、工程师、解决方案顾问、课程作者和研究写作者。

- **主要目标**：准确表达复杂结构，并快速发现标题、引用、资源和呈现问题。
- **当前阻力**：源码精确但阅读成本高；视觉编辑轻松但容易隐藏真实结构或产生不可迁移内容。
- **选择 Inflow 的理由**：既保留 Markdown 的透明度，又能理解结构和交付结果。

#### C. 本地主权用户

典型角色包括处理未公开方案、客户材料、研究草稿或受管理内容的个人与团队成员。

- **主要目标**：不依赖账号和网络完成写作，同时清楚控制内容去向。
- **当前阻力**：很多便利能力默认导入资料库、连接服务或上传内容，使用边界难以判断。
- **选择 Inflow 的理由**：核心体验离线成立，可选能力按需出现并能退出。

### 3.2 次级用户

#### D. 成熟 Markdown 工具迁移者

- 已形成稳定快捷方式、格式和文件组织习惯；
- 关注迁移后内容是否完整、常用任务是否顺畅；
- 愿意接受 Inflow 独立的信息架构，但不愿为迁移重写文件或失去基本表达。

迁移者的习惯是兼容性输入，不是产品设计模板。Inflow 保留通用平台惯例和标准 Markdown 预期，同时用自己的可信写作链组织体验。

#### E. 多文档工作区维护者

- 长期维护同一主题、项目或知识域中的多篇文档；
- 先需要直接打开普通文件夹、浏览目录树并沿相对链接连续写作；
- 随着规模增长，再需要跨文档查找、多标签、重命名、移动、删除、导航历史、关系理解和移动影响检查。

### 3.3 非核心用户

以下需求可以使用部分能力，但不作为核心产品方向：

- 只需要一次性快速记事、不关心格式和长期持有的人；
- 以多人实时协作、评论审批为主要工作的团队；
- 需要完整内容管理、社交发布、营销运营或网站搭建的人；
- 希望在编辑器中完成完整代码托管、项目管理或任意自动化的人；
- 只接受封闭视觉格式、不需要 Markdown 源内容的人。

## 5. 关键痛点与机会

| 用户痛点 | 典型后果 | Inflow 的机会 |
| --- | --- | --- |
| 不清楚“已保存”具体代表什么 | 重复保存、频繁备份、误以为内容安全 | 用可理解状态和明确选择建立文件信任 |
| 源码、预览和其他编辑方式上下文割裂 | 切换后重新定位、重复检查、害怕不同步 | 让不同视角围绕同一内容事实协作 |
| 长文档只有文本流，没有结构视角 | 查找慢、层级错误、引用和资源问题晚发现 | 把结构变成可导航、可诊断、可行动的信息 |
| 预览与最终交付不一致 | 交付旧内容、缺图、断链或排版异常 | 把交付前确认纳入同一写作链 |
| 高级能力的读取和修改边界不清楚 | 放弃使用或被迫交出过多数据 | 让能力范围、影响和退出方式对用户可见 |
| 迁移工具需要重建文件组织或学习复制品界面 | 内容锁定、迁移成本高、习惯无法延续 | 保留标准与平台惯例，同时提供独立、连贯的产品路径 |

## 6. 端到端使用场景

### S-01 创建并完成一篇本地文档

**触发：** 用户需要起草方案、技术说明或文章。

**过程：**

1. 普通启动 Inflow 后直接得到一份可编辑的未命名文档并开始输入；
2. 用户也可随时通过“文件 > 新建”或 `Command`+`N` 创建独立的未命名单文件窗口；即使当前在项目窗口中，该命令也不在项目树内创建文件；
3. 在写作中查看当前呈现，插入标题、列表、代码、表格、链接和图片；
4. 使用查找、替换、大纲和格式操作整理内容；
5. 通过“文件 > 保存”或 `Command`+`S` 选择位置和文件名，随后继续写作；
6. 交付前检查内容与资源；
7. 输出固定浅色主题的基础 PDF，随后仍可继续编辑原 Markdown；HTML 交付留到后续阶段评审。

**成功结果：** 从开始到交付不需要账号或网络；用户始终操作自己的文件，最终成果与当前内容一致。

**优先级：** 首发必备。

### S-02 接手一份已有 Markdown

**触发：** 用户从应用内、Finder、“打开方式”或拖放入口选择已有文件。

**过程：**

1. 用户可在 Finder 中直接打开 `.md` 或 `.markdown`、使用系统“打开方式”，或把文件拖到 Dock 中的 Inflow 图标或应用图标；用户可自行将 Inflow 设为这些文件的默认应用，Inflow 不静默改变系统默认关联；
2. 外部入口冷启动 Inflow 时只打开目标，不额外产生空白文档窗口；已有未修改的空白未命名窗口可直接承接目标，已有输入的草稿则保留，目标在新窗口打开；
3. 文件按原有内容、编码和资源关系打开；同一路径已打开时回到现有窗口，一次打开多份 Markdown 时每份分别打开或聚焦；
4. 用户选择适合当前任务的写作或阅读方式；
5. 修改、撤销、保存并再次打开；
6. 若文件在外部发生变化，用户看见“重新加载”提示；有未保存修改时，放弃修改前再次确认。用户若主动继续保存到原路径，则通过普通覆盖确认表达这一选择。

**成功结果：** 文件不会被隐式导入或改成专有格式；已有内容和用户选择被尊重。

**优先级：** 首发必备。

### S-03 在异常后找回未完成内容

**触发：** 应用或设备意外中断，用户重新回到文档。

**过程：**

1. 应用发现上次异常退出留下的最新轻量恢复快照；
2. 用户选择将它恢复为未命名文档，或明确放弃；
3. 恢复内容不自动写回原文件，用户检查后自行保存。

**成功结果：** 最后一次已保存文件不被恢复流程改写；未保存成果至少有一个简单、可理解的取回路径。

**优先级：** 首发必备。

### S-04 维护复杂长文档

**触发：** 文档包含多层标题、代码、表格、公式、图表、链接与本地图片。

**过程：**

1. 通过大纲快速理解层级并定位；
2. 在即时渲染编辑中直接修改常用结构，复杂块回到局部源码，并与完整源码保持对应；
3. 查找结构问题、缺失资源和异常链接；
4. 修正后再次确认完整阅读与交付结果。

**成功结果：** 用户不必在多个工具间往返，也不会因为视觉便利失去对 Markdown 的理解。

**优先级：** 个人首版只覆盖常见 Markdown、基础图片和当前仓库需要的两类 Mermaid；公式、脚注、更多图表和深度质量检查后置。

### S-05 维护一个 Markdown 项目

**触发：** 用户把一组相关 Markdown 放在同一文件夹中长期维护。

**过程：**

1. 从应用内选择文件夹，或把文件夹拖到 Dock 中的 Inflow 图标或应用图标，将它作为当前工作范围；同一项目已经打开时回到现有项目窗口；
2. 从左侧目录树切换当前 Markdown，沿项目内相对链接前往其他文档，并查看不同目录中的相对图片；
3. 通过项目树按钮或右键菜单在选定目录中新建 `.md` 或 `.markdown`；名称确认和当前文档未保存处理完成后，空文件立即写入原文件夹、出现在目录树并成为当前文档；
4. 切换前处理当前文档的未保存修改；项目外部增删改后主动刷新目录树，应用内成功新建的文件无需刷新；
5. 关闭 Inflow 后，原文件夹结构和引用仍可由其他工具直接使用；
6. 项目规模增长后，再使用跨文档搜索、多标签、快速打开、重命名、移动、删除与导航历史。

**成功结果：** 用户获得多文档组织能力，又不需要把内容迁入封闭空间。

**优先级：** 个人首版覆盖轻量文件夹项目、目录树和最多一个当前文档；成长版补齐高级工作区能力。

### S-06 使用可选专业能力

**触发：** 用户需要领域语法、专项诊断、外部连接或智能辅助。

**过程：**

1. 了解能力提供者、用途、需要读取或修改的范围；
2. 主动选择并只授权当前所需范围；
3. 查看建议、结果或可能费用，再决定是否应用；
4. 随时撤销授权或停用能力；
5. 停用后继续打开、编辑和交付标准 Markdown。

**成功结果：** 高级能力增加价值，但不成为打开文件、保存内容或理解正文的前提。

**优先级：** 专业版逐步开放，成熟版形成完整生态。

## 7. 场景优先级

| 优先级 | 判断标准 | 对应场景 |
| --- | --- | --- |
| 核心闭环 | 没有它就不能建立对本地文件和项目写作的基本信任 | S-01、S-02、S-03、S-05 的轻量范围 |
| 价值增强 | 明显提高复杂文档的连续性和可交付性 | S-04、即时渲染编辑的基础范围 |
| 规模成长 | 在轻量项目上增加搜索、多标签、重命名、移动、删除和关系能力 | S-05 的成长版范围 |
| 专业延伸 | 服务特定领域或外部服务，不得反向成为核心依赖 | S-06 |

个人首版必须完整覆盖产品负责人自己的最小真实项目闭环，而不是提前承担公共产品的全部兼容、完整 Typora 对等或发布责任。具体范围见[个人首版范围](./06-版本规划/02-首发版本范围.md)。

## 8. 用户成功信号

### 行为信号

- 用户能够从未命名文档、已有 Markdown 或普通文件夹项目直接开始工作，不经导入或格式转换；
- 用户能从项目树在预期目录创建标准 Markdown，新文件立即出现在原文件夹与目录树中；
- 用户能从目录树和项目内相对链接到达正确文档与图片，而不改变原文件组织；
- 用户能在即时渲染编辑中完成高频写作，并在复杂结构上安全回到局部源码；
- 用户在写作、阅读和交付之间完成完整任务，而不是频繁换工具验证；
- 用户在异常和外部变化后能作出有把握的选择；
- 用户持续维护原有 Markdown 和文件组织，而不是生成应用专属副本；
- 用户愿意把更重要、更长期的内容交给 Inflow。

### 体验信号

- 用户能准确说明当前内容是否已保存、成果将来自哪份内容；
- 用户切换工作方式后无需重新寻找语义位置；
- 用户能从结构提示或呈现结果回到需要修改的源位置；
- 用户能理解可选能力读取、修改或连接了什么；
- 用户停止使用某项能力或离开产品后，内容仍完整可用。

## 9. 包容性与边缘情境

目标用户定义必须覆盖不同输入方式、视觉需求和操作习惯。核心场景不应只在鼠标、默认字号、浅色外观或单一语言下成立。

产品评审必须同时考虑：

- 仅使用键盘完成高频写作和导航；
- 放大字号、提高对比度或减少动态效果；
- 中文、英文及混合内容的输入、查找与排版；
- 超长文档、大量本地资源和复杂标题层级；
- 只读、无写入权限、目标变化和资源缺失等非理想状态；
- 完全离线以及未启用任何可选能力的使用方式。
