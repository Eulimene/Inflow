## 1. 文档中心用途

本目录是一套供团队共同阅读、评审和决策的产品定义库，统一回答五个问题：

1. 为什么要做 Inflow；
2. 为谁解决什么问题；
3. 产品由哪些用户能力构成；
4. 各版本先后交付什么价值；
5. 满足什么条件才可认为产品达到预期。

这里描述用户价值、体验规则、功能范围、版本承诺和验收结果，不收录实现方案。任何产品决策都应从用户问题和产品原则出发，而不是从现有产品的功能列表反推。

## 2. 产品定义总入口

Inflow 是面向长期 Markdown 资产的本地优先写作工作台。它以“可信写作链”为产品主线，把文件可信、写作流连续、结构理解、可验证交付和安全扩展连成一条完整体验。

完整定义从[产品设计总览](./01-产品设计/00-产品设计总览.md)开始。

## 5. 推荐阅读路径

### 产品方向与立项评审

按“产品设计总览 → 产品愿景与原则 → 版本路线图”的顺序阅读，先确认用户价值和长期方向，再讨论阶段投入。

### 需求与体验设计

按“目标用户与使用场景 → 产品功能架构 → 首发版本范围”的顺序阅读。每项需求必须能回到一个明确用户任务，并说明它在完整体验中的位置。

### 产品验收与后续发布决策

同时阅读“首发版本范围”和“产品验收标准”。范围回答是否承诺，验收标准回答承诺是否真正被用户获得；二者必须共同满足。

## 6. 统一产品语言

| 术语 | 统一含义 |
| --- | --- |
| 长期 Markdown 资产 | 用户希望多年持有、可迁移、可继续编辑和反复交付的 Markdown 内容及其关联资源 |
| 可信写作链 | 从接手文件、形成内容、理解结构、验证结果到交付成果的连续体验 |
| 同一内容事实 | 编辑、分栏、阅读和其他呈现方式始终对应同一份用户内容，而不是各自保存不同版本 |
| 可解释保存 | 用户能区分内容是否已写入本地文件、是否存在待处理变化，以及下一步该做什么 |
| 可验证交付 | 用户能够确认交付成果对应的内容、资源和表达选择，并可重复获得一致结果 |
| 安全扩展 | 可选能力按用户意图加入、可检查、可停用，退出后核心写作和标准 Markdown 仍完整可用 |

四个长期产品价值阶段仍统一命名为：**首发版、成长版、专业版、成熟版**。当前且唯一的下一里程碑是 **个人首版（内部验证版）**，唯一产品用户为产品负责人本人；它不使用对外版本号，也不构成公开分发承诺。只有本人完成内部验收后，才分别决定是否开展公共预览、采用什么版本号、是否进入签名与公证、使用何种分发方式以及是否开展外部研究；正式 **1.0** 及其长期兼容、性能、可访问性和发布维护承诺同样属于后续独立决策。

## 7. 权威关系

1. [产品愿景与原则](./01-产品设计/01-产品愿景与原则.md)决定长期价值取舍，不直接扩大任一版本范围。
2. [目标用户与使用场景](./01-产品设计/02-目标用户与使用场景.md)定义核心用户任务，是需求成立的首要依据。
3. [产品功能架构](./01-产品设计/03-产品功能架构.md)定义完整产品能力边界，不代表所有能力都在首发交付。
4. 各功能设计文档定义其领域内的完整用户行为与边界；插件生态文档以同样规则定义可选能力，但不得改写核心产品。
5. [版本路线图](./01-产品设计/06-版本规划/01-版本路线图.md)决定能力进入哪个产品版本。
6. [个人首版范围](./01-产品设计/06-版本规划/02-首发版本范围.md)是当前个人首版承诺的唯一范围基线。
7. 产品附录只负责正文明确委托的规格、默认值、命令、文案和术语，不得创建新功能或改变版本归属。
8. [产品验收标准](./01-产品设计/06-版本规划/03-产品验收标准.md)是用户价值是否达标的判断基线。
9. 市场研究是决策证据，不是产品范围权威；项目管理文档管理决策和变更，不重新定义产品功能。

附录 F–H 分别承担方言与定位、能力映射、来源元数据的专项权威；它们与 A–E 一样只能精确化主产品正文已经定义的能力，不能反向创建范围。

若文档之间出现冲突，先按上述关系确定受影响的决策层，再由产品负责人发起一致性修订；不得只修改单篇文档形成隐性范围变化。本节规则由全库正式文档自动继承，专项文档只需声明自己的权威范围与关联文档，无需逐篇重复本段。

## 8. 文档状态与变更规则

统一状态为：`草稿`、`待评审`、`已批准`、`已废止`。

- `草稿`：内容仍在形成，不作为产品承诺。
- `待评审`：内容已具备完整评审条件，等待负责人批准。
- `已批准`：进入当前产品基线，变更必须记录影响并重新评审。
- `已废止`：不再有效，仅用于保留决策历史。

每次实质变更必须同步更新版本、状态和日期，并检查以下影响：

- 是否改变目标用户或核心任务；
- 是否改变产品功能边界；
- 是否改变某个版本的纳入或排除项；
- 是否改变已约定的产品验收结果；
- 是否与五大体验支柱发生冲突。

竞品观察、客户个案或内部偏好可以成为研究输入，但不能单独形成产品需求。新需求必须说明用户问题、所属体验支柱、预期结果和退出边界。

## 9. 当前评审与里程碑状态

截至 2026-09-01，当前产品文档基线已收口到 **个人首版（内部验证版）**。文档批准只确认产品定义、范围、默认值、验收标准与阶段边界，不表示功能已经实现或本人验收已经通过。当前工作区只能称为个人首版候选实现，唯一产品用户和验收者为产品负责人本人；它不是公共预览候选，也不代表已有对外版本号、签名、公证或分发产物。公共预览、版本号、签名公证、分发方式、外部研究和正式 1.0 均在本人通过个人首版验收后分别立项决定。
